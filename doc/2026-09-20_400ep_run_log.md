## §0 这一跑要回答的问题

100 epoch 那两臂（K=20 `outputs/p4_td`、K=40 `outputs/ksweep_k40`）已经把 ep30–100 走完了，
读出的是：ep40→100 续训只买到 **+0.014 / +0.034**，两者都**低于 n=100 能分辨的 ≈0.060**
（ci95 半宽 ±0.042），而 train_loss 还在掉、val 从 ep40/50 起反升
（见 [2026-09-19_ablation_record.md](2026-09-19_ablation_record.md)）。平台因此被定在 **ep30–60**。

但这条判读**只覆盖到 ep100**。ep100 之后是什么样，此前从没测过：

- 「ep30–60 就是天花板」——没测过 ep100 以后，这句话的外推没有数据
- 「ep100 后又开始爬」——同样没人测过，**没有被排除**

两个假设都还开着，而且它们给出的工程结论完全相反（一个说收手，一个说继续加 epoch）。
**这一跑就是来关掉这个区间的。** 它不是 100 epoch 那两臂的重跑，也不是续训。

> 与 100 epoch 臂的关系：**同 config、同 seed、同数据、同协议**，差别是 `--epochs 400`
> （而非 40）、**从头初始化**、以及 **`--ckpt-epochs` 网格不同**（旧臂每 10，本跑每 5）。
>
> ⚠️ **最后那一条使这两条曲线不可逐点对照。这是启动当天（09-20）实测出来的，见 §9。**
> 我原先在这里写「ep5…ep100 可以与旧臂逐点对照，顺带构成一次重跑一致性检查」——
> **那句话是错的**，已由 §9 的 md5 与逐步 loss 对比推翻。

## §1 两臂配置（为什么只有两臂）

| | K=20 | K=40 |
|---|---|---|
| 卡 | **GPU1** | **GPU2** |
| config | `configs/pusht_dino_p256_td.yaml` | `configs/pusht_dino_p256_td_k40.yaml` |

`scripts/make_k_configs.py` 生成的，带 4 行生成器头注释；`diff` 出来是：

```
           > # Anchor-count sweep: ...   (> 共 4 行注释)
```

配对均值 +0.0562±0.0121）。K=5/K=10 不再续训。

## §2 ckpt 网格与 rollout 节奏

- `--epochs 400`，**从头初始化**（无 `--resume`）
- `--ckpt-epochs $(seq -s, 5 5 400)` → **每 5 个 epoch 存一次，80 个/臂**
- rollout 节奏 = **每个 ckpt 一次**，即每 5 epoch 一次，**ep5…ep400 共 80 次/臂**

80 这个粒度是刻意的：平台若真在 ep30–60，5 epoch 的分辨率才看得出它是否**动过**；
10 epoch 会把早期平台抹平。（`train.py` 的 `eval_freq_epochs`（=10）只控**验证 loss**，
与 rollout 节奏无关，两臂都保持 10 不变。）

### rollout 协议（与既有各臂逐字一致）

```
--num-evals 100 --num-envs 10 --rng-seed 0 --train-seed 0
```

n=100 不是可以省的地方：**这是唯一能分辨 ≈0.060 差异的样本量**，而这一跑要判的正是
「平台是否移动」——用 n=20 跑出来的曲线，点与点之间的抖动和真信号同量级，
平台看起来会像噪声。用户 2026-09-20 明确选了 **n=100（同既有协议）**。

### ckpt 剪枝规则（keep-best）

`train.py` **不写 best ckpt**（`grep -n "best" patch_policy/train.py` 返回空），
「最佳」只能由 driver 在 rollout 之后按 `base_metrics.final_coverage_mean` 判定。
每个点 rollout 完成后保留：

```
keep = { 当前 best,  最新的一个,  刚刚评估完的那一个 }
```

- **best** 是这一跑的全部意义
- **最新**是训练若中途死掉时唯一的 resume 点
- **刚评估的**受保护，否则 rollout 会删掉自己正在读的输入

训练进程退出后**收敛到只留 best**（`~0.5 GB/臂`，而非 ~37 GB/臂）。
用户 2026-09-20 选的就是 **只留 best（~3 GB）**。

保留 best 而不是全删的理由：best ckpt 是后续用 `rng_seed=1,2` 做多次复评的唯一凭据
（`rollout_locked_gpu0.sh` 第 5 个参数就是为此设计的）。中间 epoch 只留
rollout JSON/CSV/NPZ —— 那正是对比表需要的，体积可忽略。

## §3 ⚠️ 这一跑的计时数字**不能当计时用**

用户 2026-09-20 的排卡是「GPU1、GPU2 训练，GPU0 做 rollout」。这是明确的、被接受的取舍，
代价记在这里，**以免后人不小心把这些毫秒平均进任何对比**：

1. **GPU0 是热限的那张卡。** 带负载 84–88 °C、SM ~1090 MHz，是一张凉卡的 **52 %**。
   项目既有硬规则：**「计时对比必须避开 GPU0」**（见记忆 `gpu0-thermal-throttle`）。
2. **它与两个训练并发。** 本机并发把每步墙钟抬高过 **~2.9×**，
   `encoder_ms` 是那支温度计（干净时 16.6–17.1 ms，被争抢时 48–58 ms）。

> **结论：这一跑产出的 `final_coverage` / `success` 有效；`policy_ms` / `encoder_ms` /
> `total_ms` 无效。** 计时对比必须来自之后在凉卡上**独占**重跑的那一次。
>
> `encoder_ms` 仍值得读——不是当持续时间，而是当**温度计**：它告诉你某一次 rollout
> 是否在被争抢的状态下跑的。形状完全相同的 DINO 工作，它的墙钟只反映机器负载。

用户对此的原话是「**只要 coverage 曲线，放弃这次计时**」。

   否则误重启会悄悄接上半成品，而产出的曲线既不是旧的也不是新的，却会被当成一条
   干净的 400 epoch 曲线来读

### rollout worker

两个独立进程，**一臂一个**：

```bash
cd ~/td_pusht && ( setsid nohup bash scripts/run_400ep_rollout.sh 20 \
    > logs/run400ep_rollout_k20.log 2>&1 < /dev/null & )
cd ~/td_pusht && ( setsid nohup bash scripts/run_400ep_rollout.sh 40 \
    > logs/run400ep_rollout_k40.log 2>&1 < /dev/null & )
```

```
=== 400ep rollout worker K=20 start 2026-09-20 08:38:31 ===
=== 400ep rollout worker K=40 start 2026-09-20 08:38:33 ===
```

**为什么是两个进程而不是一个按 epoch 同步的循环。** K=40 每 epoch 比 K=20 慢约 1.4×；
若两个臂在同一个循环里按 epoch 对齐，K=20 剩余的点会被 K=40 拖住**好几天**。
两个 worker 各自按自己那臂的节奏推进，它们之间**只在 GPU0 上**通过
`rollout_locked_gpu0.sh` 的 flock 串行——那是它们唯一共享的东西。

**锁必须是同一把。** 两个 worker 都打 GPU0：每次 n100 峰值 ~10 GB，24 GB 卡上两个同时跑
就是 OOM 或互相拖慢，而两者都会「以为自己独占」。`rollout_locked_gpu0.sh` 的锁是绝对路径
`~/sibling_pkg/audits/gpu0_rollout.lock`，两个 worker 共用它。
（GPU0 的锁与 GPU2 的锁**故意不是同一个文件**——不同卡，两个 rollout 可以合法地同时跑。）

### restartable

已有 `rollout/ep{N}/rollout_seed0.json` 的 epoch 会被**跳过**，所以 worker 可以在任何时刻
被杀掉再拉起，不会重复劳动。这也是断电/重启后的恢复方式。

## §5 启动时抓到并修掉的一个缺陷（留档）

第一次拉起 worker（08:36:47/08:36:48）之后发现：**服务器上跑的 `run_400ep_rollout.sh`
是重构之前的版本**。`wait_ckpt` 重构是在最后一次 `sync.py` **之后**做的，而拉起 worker
的命令没有重新同步——服务器那份还是 **178 行、`grep -c wait_ckpt` = 0**。

旧版在「等待超时但训练仍活着」时会 `continue` 进入下一个 epoch。那会**静默跳过曲线上的一个点**
——而**空洞正是这一跑存在的意义所要避免的东西**。K=40 在被争抢时每 epoch ~1400 s，
5 个 epoch 就可能超过等待预算，所以这条路径不是理论上的。

处理：杀掉两个 worker → `python scripts/sync.py`（62 files）→ 确认服务器脚本
**201 行、`wait_ckpt` 存在、CR 字节 = 0**（二进制读，权威）→ 重新拉起。

**没有丢任何工作**：两个 worker 当时都还在启动横幅之后、epoch 循环里等 ep5，
`outputs/p4_td_400ep/rollout` 与 `outputs/ksweep_k40_400ep/rollout` **两个目录都还不存在**
（即 0 次 rollout 已完成）。两个训练全程未被触碰（重同步后仍是 pid 3681948 / 3682135，
step 1060，梯度探针 6 项全 `ok`）。

重构后的 `wait_ckpt` 语义：**训练活着时超时不等于该 epoch 没了**。超时后最多重等 4 个周期
（每周期 `WAIT_MIN`=240 min），其间继续等；只有「ckpt 不在 **且** 背后没有训练进程」才判定
该 epoch 真的不存在。这条规则被写进脚本头注，因为它是这个文件里最容易改错的一处。

```bash
        pts.append((ep, m['final_coverage_mean'], m['success_rate_095']))
```

> 并存，是两套不同样本量的评测；不加过滤时会读到 n=20 的那个
> （实测：K=20 ep30 读成 **0.8210**，而 n=100 的真值是 **0.6149**，差 +0.206）。
> 本跑的目录内只有 `epN` 一种形态，但读旧臂时必须过滤。

**JSON 字段位置（实测过，别再猜）：**

| 想读的东西 | 在哪 |
|---|---|
| `final_coverage_mean` `success_rate_095` `n_episodes_reached_095` `final_coverage_ci95` `policy_ms_per_step_mean` | **`base_metrics` 层** |
| `final_coverage` `max_coverage` `success`（bool）`encoder_ms` `policy_ms` | **顶层 `episodes` 列表**里，每条一个 episode |

`base_metrics` 里**没有** `episodes` 这个键——它是**顶层**的，且实测是 **100 条**（每条一个
episode 的 dict），不是空列表。**做双峰/分箱分析必须读顶层 `episodes`**：mean 是个人头读数，
`mid bin` 里只有 5–15/100 的时候，mean 落在空隙里、`median` 描述的是成功簇
（见 [2026-09-19_ablation_record.md](2026-09-19_ablation_record.md) §B.2）。

另注：旧臂的 rollout 目录名**不统一**（`outputs/p4_td/rollout/` 下 `ep10` 与 `ep10_n100` 并存，
`outputs/ksweep_k40/rollout/` 下只有 `ep10` 形态）。本跑的 worker 一律写 `ep${EP}`
（`mkdir -p "$ROLL/ep${EP}"`），所以本跑目录内是一致的；上面脚本用正则取数字，两种都能读。

## §9 实测发现：`--ckpt-epochs` **不是**被动的观察旋钮

09-20 首次读曲线时（本跑已到 ep31 / ep22），把本跑与 100 epoch 旧臂在同 epoch 上并排，
发现对不上，且**方向不一致**（K=20 有正有负、K=40 全负）。逐层查到根因，证据链如下。

### 9.1 现象

### 9.3 ckpt 不是只差元数据 —— 权重真的不同

`outputs/p4_td/seed0/ckpt_epoch30_step86760.pt`（旧，09-16）与

按日志里逐步 loss 序列找第一个不同的 step：

```
FIRST DIVERGING LOGGED STEP: 14470

   step  14470  old=0.8020  new=0.7775   <== DIFF
```

`14470 / 2892 步每 epoch = 5.003` ⇒ **恰好是 epoch 5**。

`train.py:1289` 是：

```python
if e % cfg.eval_freq_epochs == 0 or e in ckpt_epochs:
    ...  # 验证
if e in ckpt_epochs:
    save_ckpt(e)
```

`eval_freq_epochs = 10`，但 **`e in ckpt_epochs` 也是一个触发条件**。于是：

| | `ckpt_epochs` | 验证发生在 |
|---|---|---|
| 旧臂（P4） | 10,20,30,40 | ep10, 20, 30, 40 |
| 本跑 | 5,10,15,…,400 | **ep5**, 10, 15, 20, … |

本跑在 **ep5 多做了一次验证**，旧臂没做。分叉点正好是 ep5 ⇒ **验证过程改动了训练轨迹**。

### 9.5 机制：验证走 `forward` → `_calc_loss`，那里的噪声取**全局 RNG**

`patch_policy/td_head.py` 有两处 `torch.randn`，一个钉了 generator，一个没钉：

| 位置 | 调用方 | generator |
|---|---|---|
| `:874` `_sample()`（推理，`@torch.no_grad()`） | rollout | `generator=self._gen(...)` —— **已钉**，可复现 |
| `:954` `_calc_loss()`（**训练**） | `forward()` | **无 generator** —— 消耗**全局 torch RNG** |

验证 loss 是通过 `forward()` → `_calc_loss()` 算的，因此**每次验证都从全局 RNG 里抽掉一批数**
（每个 val batch 每个 (n,t) 位置一次 `randn`），训练侧后续所有依赖全局 RNG 的抽样
（数据顺序等）随之整体错位。ep0 的验证两跑都做 ⇒ 到 step 14460 仍逐位相同；
ep5 只有本跑做 ⇒ 从 14470 起分叉。这与观测完全吻合。

> 注意这**不是本跑引入的 bug**，而是既有 harness 的性质；本跑只是第一个
> `ckpt_epochs` 比 `eval_freq_epochs` 更密的运行，把这个性质暴露出来了。

### 9.6 后果（这条影响到什么）

1. **本跑与 100 epoch 旧臂不可逐点对照。** §9.1 的那些 Δ **不是**「重跑不一致」，
   而是两条**不同的**训练曲线之间的差 —— 里面同时含有 ckpt 网格导致的轨迹分叉，
   以及抽样噪声。旧臂的曲线仍然是旧臂自己的有效记录，本跑的是本跑的；两者不能互相印证。
2. **`--ckpt-epochs` 是实验变量而非观测手段。** 任何两次比较，若 ckpt 网格不同，
   就不构成单变量对比。P6 的三臂对比必须让三臂的 ckpt 网格**逐字相同**（原计划已如此要求），
   现在这条从「整洁起见」升级为**数值正确性前提**。
3. **同一 ckpt 的 rollout 本身仍可复现**（`_sample` 的 generator 已钉），
   所以 n=100 的单点抽样噪声地板不受本条影响；受影响的只有「训练轨迹」。

### 9.7 本跑要不要改

**不改。** 分叉已在 ep5 发生，此刻改 `--ckpt-epochs` 不会倒回 ep5；而重跑一遍要再花数天，
且**新网格同样会与旧臂不同**（旧臂是每 10，任何每 5 的网格都会在 ep5 首次分叉）。
本跑作为「ep100 之后会怎样」的独立观测仍然完全成立 —— 它只需要**自己内部**可比，
而它内部从头到尾都是同一个网格。**唯一失效的是与旧臂的逐点对照**，那本来只是顺带的好处。

## §10 训练速度实测

**09-21 09:42 读取。** 这一节只放**训练**的墙钟（rollout 的墙钟另有其数，见 §10.5 末）。
与 §3 相反，训练速度**不受**「毫秒无效」那条约束影响：两个训练各自独占 GPU1 / GPU2，
§3 说的是 GPU0 上 rollout 的 `policy_ms` / `encoder_ms`。**epoch 墙钟是可用的。**

### 10.1 数据从哪来 —— 两个互证的来源

**来源 A：训练日志的 `[epoch N/400] val_loss=… (Xs)`。** 读法如下（这是本跑第一次把它写清）：

- 该行**只在验证发生时打印** —— `train.py:1289` 的条件是
  `e % eval_freq_epochs == 0 or e in ckpt_epochs`，`eval_freq_epochs=10`、本跑 ckpt 网格每 5，
  取并集 ⇒ **每 5 个 epoch 一条**。所以 K=20 到 ep105 只有 22 条（ep0,5,…,105），
  K=40 到 ep70 只有 15 条。**它不是每个 epoch 都打。**
- 括号里的数是**该进程启动以来的累计墙钟秒数**，**不是**该 epoch 的耗时。
  （§6 原先写反了，已在那里更正。）
- 于是 `Δ(两条的括号) / Δ(epoch 号)` = 该区间的 s/epoch。这是**日志自带**的测速，不需要 ckpt。

**来源 B：ckpt mtime**（`stat -c "%y %n"`）。worker 剪枝后每臂只剩 2–3 个 ckpt，
所以窗口很长（K=20 跨 60 epoch、K=40 跨 35 epoch）——长窗口反而更稳，代价是点少。

**互证**：K=20 ep105 的 ckpt mtime `09-21 08:47:03` 减启动时刻 `09-20 08:31:59` = **87304 s**，
日志同点 = **87256 s**，差 48 s（进程启动开销）。两个来源一致 ⇒ 下面的数不是单点偶然。

### 10.3 VQ-BeT 参照线可比到什么程度

这一行来自 `~/patch_policy/outputs/pusht/phase9/dino_s43` —— **上游只读仓库**，
不是本工程的 harness（红线：不改不复制，此处只读)。用 `completion_idx_{4,9,…,99}.json`
的 mtime 求差，间隔稳定在 **875–885 s / 5 epoch**。

**可比的：** 比的是 **s/epoch 墙钟**，它含数据加载 + DINO 前向 + 反向 + 优化器步。
这些环节与两臂同源：同 dataset、**同 `dataloader batch size: 8`**、同 DINOv2 ViT-S/14、
同 `n_patches 256` / `window_size 5`。而且 `supervisor.log` 显示它**当时也是三路并发** ——
`dino_s43` 在 GPU1，与 GPU0 的 `vtp_s44`、GPU2 的 `dino_s44` **同秒（08-23 22:34:11）启动** ——
与本跑现在的排卡同构。

**不可比 / 要打折的：**

1. **不同代码基。** phase9 是上游 `patch_policy`（`models/`+`datasets/`+`utils/` 布局），
   本跑是本工程的 fork（`patch_policy/` 单层）。P0 已证两者逐文件「模包名恒等」，
   但**不是同一份进程、不是同一棵树**。
2. **日期不同**（08-23/24 vs 09-20/21），机器状态不可能完全一致。
3. **VQ-BeT 那个数里含每 5 epoch 一次的 in-loop env eval。** `eval_on_env` 在训练进程内跑，
   其完成时刻与 `completion_idx_N.json` 的 mtime 重合到同一秒
   （日志 `23:41:11.182` vs 文件 `23:41:10.69`）。本跑**没有** in-loop env eval
   —— rollout 是 GPU0 上的独立 worker，不占训练的 epoch 墙钟。
   所以 **878.8 s/epoch 是 VQ-BeT 每 epoch 训练耗时的「上界」**，它的纯训练只会比这更快。
   ⇒ 表里「TD K=20 比 VQ-BeT 快 5.9%」这句话，**方向上是对 TD 不利的**：
   拿掉 eval 后 VQ-BeT 很可能反超。**不要把这个 5.9% 当成 TD 的头更快的证据。**
4. phase9 的日志只打了 `dataloader batch size: 8`，**没打 windows 数**，所以
   「它的步/epoch 也是 2892」是**推断**（同 dataset、同 batch、同 split），未逐字核对。
   **s/epoch 与 min/epoch 两列不依赖这条；`steps/s` 一列依赖它。**
