# Attention kernel：手写链 → SDPA（2026-10-27）

**一句话**：本仓库的三处 attention 现在有第二个实现——`F.scaled_dot_product_attention`。
它跑的是**同一个数学**（同一 mask、同一 head 布局、同一 dropout 位置），只是不再物化
`[B, nh, T, T]` 分数矩阵。**默认仍是手写链**，`doc/` 里所有数字据此复现；SDPA 是
`--attn sdpa` 打开的开关。

**为什么现在做**：那份 SDPA backend 审计任务书原本是给生产线
（Patch Policy + Flow Matching）做 SDPA backend 审计的。审计在**姊妹线**上做完了，结论是
fp32 走 mem-efficient、bf16 才落到 FlashAttention-2，合并 AMP 后 288.01 → 125.66 ms/step
（2.29×，显存 9001 → 4249 MB）。本仓库的 trunk 是同一份 `gpt.py`，所以把开关移植过来，
而不是各写一份。

**这不是一次「调参」**：模型结构、mask、`is_causal`、dropout 概率、残差路径、损失、
优化器、数据全部未动。改动面就是 kernel dispatch。

---

## 1. 改了什么

| 文件 | 改动 |
|---|---|
| `patch_policy/gpt.py` | `CausalSelfAttention.attn_impl`（默认 `"current"`）+ sdpa 分支；新增 `ATTN_IMPLS` 与 `set_attn_impl()` |
| `patch_policy/global_policy.py` | `GlobalSelfAttention` 同上（它的 mask 是「state 互联 / query 全看」，不是 block-causal） |
| `patch_policy/td_head.py` | `CrossAttention` 同上。这一处**没有 mask**，是三个点里最干净的 |
| `patch_policy/train.py` | `--attn {current,sdpa}`；默认 `None` = 不动模块默认值。非默认值命中 0 个模块时 `SystemExit`，不静默 |
| `tests/test_attn_sdpa.py` | 15 项 parity / mask 语义 / dropout 位置 / selector 契约（新增） |

`set_attn_impl` 放在 `gpt.py`：它同时覆盖三处 attention，**只此一份定义**，
`train.py` 调它；语料里写死 `ATTN_IMPLS`，未知 kernel 抛 `ValueError`。

`--attn` 的落地位置在 `build_model` 之后、`configure_optimizers` 之前——在优化器建组之前
切换，避免「kernel 换了但 param group 已经按旧图建好」这类隐患。

## 2. 为什么不把默认改掉

`doc/` 里 P2/P3/P4/K-sweep/400ep 全部是手写链跑出来的。SDPA 与手写链**数学等价但求和顺序
不同**，逐 step 累积会让轨迹分岔——FM 线在 fp32 对照里已经量到 `loss_last` 0.1265 vs 0.1276。
所以：

- 默认 `"current"` ⇒ 历史 run **逐位**可复现；
- `--attn sdpa` ⇒ 要速度时显式打开，并在 log 里留下 `[attn] kernel=sdpa on N module(s)` 一行，
  读 run log 的人立刻知道这份数字属于哪个 kernel。

「换成 SDPA 之后结果一样」这句话**不能说**。能说的是：损失面、梯度尺度、收敛趋势一致，
最终权重不会逐位相同。

## 3. 证据一：parity（本机实测）

`python tests/test_attn_sdpa.py` —— 15 项全过。数值（`current` vs `sdpa`，同权重同输入，eval 模式）：

| 位置 | dtype / shape | max_abs | mean_abs |
|---|---|---|---|
| trunk `CausalSelfAttention` | fp32, S=48 | **8.94e-08** | 1.13e-08 |
| `GlobalSelfAttention` | fp32, T=8 | **1.19e-07** | 1.73e-08 |
| `CrossAttention`（`ctx_dim≠d_model`） | fp32, Q=20/M=5 | **1.79e-07** | 1.80e-08 |
| GPT trunk 端到端 readout | fp32, 2 层 | **3.58e-07** | — |
| trunk 生产形状 | **bf16**, S=1280, nh=8 | **4.88e-04** | 4.32e-05 |

fp32 全部落在**舍入量级**（<1e-6），即「同一数学的另一种实现」，不是近似。
bf16 的 4.9e-4 是**低精度 kernel 的正常差异**（长归约 S=1280 上累加顺序 + bf16 存储），
测试里给的容差 1.5e-2 是留给不同后端/不同卡的余量，不是给「算错了」的余量。

## 4. 证据二：mask 语义（真正容易改坏的地方）

`generate_block_causal_mask` 的 `True` == 可参与，正好是 SDPA 的 bool 约定，
所以 `attn_mask=mask` 与 `masked_fill(~mask, -inf)` 等价。测试直接把这件事钉住：

- 手写链 vs SDPA 在非对称 mask 上逐元素一致：**1.19e-07**；
- **最后一个块**的 key 加 1.0，前两个块的输出**逐位不动**（`max_abs_past = 0.00e+00`），
  而它自己那个块动了（`3.73e-02`）——causal 关系没有被抹平或加严。

`is_causal=False` 是硬约束：block-causal 结构已经在 mask 里，再传 `True` 会**二次**施加
严格下三角 mask，等于偷偷改 token interaction。谁把它改成 `True`，上面这条测试立刻红。

## 5. 证据三：本机 kernel 与速度（RTX 4060 Laptop，torch 2.3.0+cu118 / CUDA 11.8）

真实 trunk：8 层 / 512 dim / 8 head / block_size=5 / n_patches=256（S=1280），
batch 4，forward+backward+AdamW，warmup 3 / 计时 10 step，CUDA Event 计时。

| dtype | kernel | ms/step | peak VRAM | 倍率 |
|---|---|---|---|---|
| fp32 | current | 356.97 | 3751 MB | — |
| fp32 | **sdpa** | **263.87** | **1748 MB** | **1.35×**（显存 −53%） |
| bf16 | current | 148.50 | 1900 MB | — |
| bf16 | **sdpa** | **73.53** | **902 MB** | **2.02×**（显存 −53%） |

**实际跑到哪个 backend**（profiler 读出来的，不是按 flag 猜的）：两种 dtype 都是
`aten::_efficient_attention_forward`（mem-efficient）。这台机器的 torch 是 Windows 构建，
**没有编译 FlashAttention**（`Torch was not compiled with flash attention`），
强制 `SDPBackend.FLASH_ATTENTION` 直接 `RuntimeError: No available kernel`。
所以：

> **「SDPA」不等于「FlashAttention」。** 选到哪个 fused kernel 由 build + dtype + mask + 卡决定。
> flash 后端只吃 fp16/bf16，且需要在 Linux 版 torch 上编译进二进制。本机拿到的是 mem-efficient；
> 生产 3090 上 bf16 才落到 FA-2（见 §6）。**不要拿本表的倍率去外推 3090。**

## 6. 证据四：生产线的实测（**不是本仓库的数字**）

同一开关在 Patch Policy + FM 线（RTX 3090，batch 8，PushT 全量 206 episode，
23136 windows ⇒ 2892 step/epoch）上的长期实测：

| 配置 | ms/step | samples/s | peak VRAM | 判据 |
|---|---|---|---|---|
| FP32 真实基线 | 288.01 | 27.78 | 9001 MB | — |
| FP32 + SDPA | 258.17 | 30.99 | 5252 MB | forward 97.71→74.10，backward 基本不动 |
| **bf16 + SDPA** | **125.66** | **63.66** | **4249 MB** | forward 32.84 / backward 76.65 |

50 epoch 长期 run 实测 394.6 s/epoch（6.58 min），合计 ≈5.49 h；相对 FP32 基线 **2.29×**。
那里的结论是「省显存」和「省时间」在 bf16 上是同一个开关的两面：fp32 只能落 mem-efficient
（只省显存），bf16 才落 FA-2（时间和显存一起省）。

**归因必须写清楚**：以上是 FM 臂的数字。本仓库的 TD 臂**没有**在 3090 上重测过 kernel，
只做了（a）parity、（b）本机 4060 的 kernel 与速度、（c）`--attn` 管线验证。
把 FM 的 2.29× 当成 TD 臂的加速比是**错**的——架子上少了 AMP 那一半。

## 7. 没做的事

- **没有跑任何训练**（不碰长训练，按 FLashAttention.md 的任务书）。`doc/` 现有数字全部来自手写链。
- **没有改默认 kernel**（理由见 §2）。
- **rollout / eval 路径保持 `current`**：`eval_rollout.py` 不设 `attn_impl`，复用了模块默认值。
  这是**故意**的——rollout 的计时要和历史 n=100 结果可比。要提速得单独接，并单独记一份计时。
- **没有 AMP**。本仓库的 `train.py` 没有 `--amp`；SDPA 单独在 fp32 上是 1.35×，
  只有和 bf16 合并才是 FM 那个 2.29×。这是下一步，不是已完成项。
- **没有在 3090 上测 TD 臂**，也没有 `torch.compile`。
- 本机没有 `vector_quantize_pytorch`，`tests/test_attn_sdpa.py` 里 global/cross 两处会打印
  `SKIPPED` 而不是假装通过；服务器上（有该依赖）会真跑，本机用 stub 跑过一遍确认 15/15。

## 8. 怎么用

```bash
# 默认：手写链，历史数字可逐位复现
python -m patch_policy.train --config configs/pusht_dino_p256_td.yaml

# 打开 SDPA（log 里会出现 [attn] kernel=sdpa on 3 attention module(s)）
python -m patch_policy.train --config configs/pusht_dino_p256_td.yaml --attn sdpa

# kernel 正确性（15 项，纯 torch，不需要 diffusers）
python tests/test_attn_sdpa.py
pytest tests/test_attn_sdpa.py -q
```

## 9. 复现本页数字

```bash
python tests/test_attn_sdpa.py          # §3 §4 的 parity / mask 表
python -m patch_policy.train --help     # §1 的 --attn 契约（需服务器环境，本机缺 VQ 依赖）
```

§5 的 benchmark 是一次性脚本（trunk forward+backward、CUDA Event、warmup 3 / 计时 10），
未入库：它测的是**这台 4060**，换卡即失效；要重测就在目标卡上重跑同样的协议。
