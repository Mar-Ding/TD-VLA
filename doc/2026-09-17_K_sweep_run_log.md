> **Scope note (2026-09-19).** The sweep itself is the 40-epoch, three-arm run described
> below. **K=40 was later resumed to ep100** (§13) and so was K=20 (which lives in
> `2026-09-16_P4_run_log.md`, Addendum C); K=5 and K=10 were not, and remain at ep40.

**What this file is.** A pure record of one sweep: three concurrent trainings that differ
in EXACTLY two config lines (`td.n_modes` and `td.anchor_artifact`), plus the twelve n=100
rollouts run afterwards. It holds the configurations, the launches, the environment, the
data split, the wall clock, the full loss traces and the rollout metrics — and nothing
else. Every derived number in the K-sweep report comes from this file, and every number in
this file was read back from the sweep's own artifacts on disk.

**Read-back commands** (all from `~/td_pusht`, all read-only):

## 2. Launch

`scripts/run_k_sweep.sh` carries `ARMS="5:0 10:1 40:2"` (K:GPU), `EPOCHS=40`,
`CKPT_EPOCHS=10,20,30,40`, `TRAIN_SEED=0`. Each card has a busy-guard that refuses to
start if `nvidia-smi -i "$GPU" --query-compute-apps` returns non-empty; the config sanity
checks are CRLF-tolerant. Launch line, one per arm:

```bash
nohup env CUDA_VISIBLE_DEVICES=$GPU ~/miniconda3/envs/wemm-p1/bin/python -u \
    -m patch_policy.train --config "$CFG" --train-seed 0 --epochs 40 \
    --ckpt-epochs 10,20,30,40 --save-dir "$OUT" > "$LOG" 2>&1 &
```

`steps/epoch = 23136 train windows / batch_size 8 = 2892` (ceil); 40 epochs = **115,680
steps**. `eval_freq_epochs = 10`, so `val_loss` exists only at ep10/20/30/40.

Two independent methods cross-check, and agree to 0.1–1.0 %: `steps_per_epoch / steps_per_s`
vs the marker differences. P4's solo reference on the same box was 3.014 steps/s =
959.4 s/epoch.

**These wall clocks are not a K-cost ordering.** K=5 is 1.6–1.8× slower per epoch than K=10
on a *smaller* head, because it ran on the thermally capped GPU0 (§3). K=5's own last
segment fell from 13,575 s to 10,493 s as the other two arms finished and stopped competing
for host-side resources — i.e. its rate moved with its neighbours. K=10's four identical
8,250 s segments are the cleanest readings in this table; note they are still *faster* than
P4's so-called solo 959.4 s/epoch, so that reference has at least ±10 % of drift in it.

### 7.1 Recorded fact: `val_loss` and rollout coverage point in opposite directions

Every arm's `val_loss` is **minimal at ep10, the first evaluation point, and rises
monotonically thereafter** (+36.1 % / +21.2 % / +19.3 % from ep10 to ep40), while
`train_loss` falls the whole way down. The train/val gap at ep40 is 1.562 / 1.247 / 0.745.

The rollout coverage of the *same checkpoints* (§8.3) rises rather than falls, and for K=10
and K=40 it rises monotonically to the last checkpoint. All three arms' best coverage is at
**ep40**, the last checkpoint, with no plateau visible.

Because the sweep only evaluated val every 10 epochs, the location of the true val minimum
is not observable from this run — the data establishes only that ep10 is already past it.
No interpretation of that fact is recorded here; it is noted because §7's table and §8.3's
table must not be read as agreeing.

## 8. Rollouts

### 8.1 Launch

Run **after all three trainings finished**, strictly serially, on GPU2 only, by
`scripts/run_k_rollout.sh` → `scripts/rollout_locked_gpu2.sh`. The lock is the absolute
path of the one real lock file also held by the sibling driver
(`~/sibling_pkg/audits/gpu2_rollout.lock`); a relative-path lock would let both
drivers each acquire "their own" lock and run concurrently while both believed they were
serialized. No concurrency at any point: 12 rollouts, one at a time, `compute_apps=none`
before and after every one.

### 8.5 Determinism

`[eval] action-sampling RNG seeded AFTER init/ckpt load: torch.manual_seed(0) +
cuda.manual_seed_all(0)` appears in all 12 logs, and `episode_steps_mean` is 302.0000 in all
12. No cross-run determinism check was performed for this sweep (the P4 log's §A.4

## 13. Addendum 2026-09-19 — the resume was run; K=40 went to ep100 (and so did K=20)

The question §12 left open ("has a plateau been reached?") is now answered by execution, not
by inference. Driver: `scripts/run_resume_to100.sh`, launched 2026-09-18 with the user's
per-arm GPU assignment (K=20 → GPU1, K=40 → GPU2, the only time this project trained off

50,699 s; K=40 finished 15:32:04 after 70,242 s.** Six new ckpts per arm
(ep50/60/70/80/90/100), ~500 MB each. All 10 ckpts of each arm are on disk; nothing pruned.

**Resume correctness was gated before launch, not assumed.** `scripts/probe_resume.py`
(12 gates/arm: Adam slot count 160 == 160 trainable tensors, optimizer layout byte-identical,
recorded LR `[5.5e-5]×3` == yaml, RNG incl. the `dataloader` stream, metrics history reaching
ep40, `vqvae_is_fit True`, anchor artifact hash, config-vs-K match) — 12/12 PASS on both arms.
Continuity is structural and the code lines are cited so it can be re-derived:
`range(resume_epoch, cfg.epochs)` (`train.py:1088`) → e=41..100 exactly, ep40 not retrained;
constant LR with no scheduler/warmup/decay (`train.py:920`) so there is no schedule to
re-enter; `metrics.json` merged (`train.py:1060-1067`) so the curve does not restart at e=1.

**Both §11's and §12's convergence statements are superseded.**

- §11 "**No convergence plateau reached**: all three arms' best coverage is the last
  checkpoint." → **false for K=40**: its best n=100 point is **ep60 (0.6466)**, not ep100
  (0.6172). Still true for K=5/K=10, which were not resumed and remain at ep40.
- §11/§12 "ep40 is a training that stopped on a schedule, not one that converged." → the
  plateau **is** now located: it arrived between **ep30 and ep60**. Mean coverage over
  ep10–40 → ep50–100 moved **+0.014** (K=20: 0.5287 → 0.5428) and **+0.034** (K=40: 0.5732 →
  0.6068) while train_loss kept falling to 0.16. The minimum difference two n=100 rollouts
  can resolve is **≈ 0.060** (ci95 half-width ±0.042), so **neither gain is statistically
  distinguishable from zero** — 60 more epochs bought no measurable control improvement.
  Train ↓ / val ↑ / coverage flat is the signature of **overfitting**, not of undertraining.
